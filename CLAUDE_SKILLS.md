# Claude Skills integration

Harness can catalog local Claude skill files from the selected workspace's `.claude/skills` directory and an explicitly selected personal skills directory. It returns bounded display metadata, source scope, a stable opaque ID, the `SKILL.md` content hash, and a disabled activation state. This establishes the desktop integration point; it does not implement the Claude native adapter or activate skills in Codex.

## Native compatibility evidence

Checked **2026-09-06** against the official [Claude Code skills documentation](https://code.claude.com/docs/en/skills). Claude Code supports project and personal skill directories plus other sources, including plugins and nested directories. For project/personal skills, the directory determines the command; an optional `name` supplies the display label. Frontmatter is optional and belongs on the first line. Invocation flags, tool declarations, model selection, forked contexts, hooks, supporting files and dynamic shell content can affect native execution. Discovery can follow links and native source precedence can select among duplicate names. These behaviors require native compatibility tests before Harness enables execution. Claude Code extensions also differ from the fields accepted by the Skills API and claude.ai uploads, so a file catalog does not establish portability between those products.

## Implemented host boundary

The privileged `discoverClaudeSkills` operation receives a host-resolved `WorkspaceDescriptor`. It reads only immediate `<skill>/SKILL.md` files below that workspace's `.claude/skills` directory. A `userSkillsRoot` is included only after the user explicitly authorizes that directory. The function never infers the home directory, imports a plugin, reads native credentials/settings, launches a process, fetches remote content, or executes a skill.

The browser receives `SkillCatalog` from `@harness/protocol`; filesystem code stays in the control plane's privileged host entry point. The native desktop folder picker authorizes roots. Renderer-supplied paths must never flow directly to this operation. Display fields are untrusted text, not HTML, Markdown instructions, shell arguments or an instruction source for an agent. The catalog omits skill bodies, referenced content, absolute skill paths, unknown metadata values and raw filesystem errors. Frontmatter descriptions remain user-provided content; they may contain sensitive text and should not enter ordinary telemetry.

Discovery is a bounded snapshot, not a native active-skill listing. Each scan permits 256 directory entries by default, across both roots, with a configurable hard maximum of 2,048. Files are limited to 64 KiB by default, at most 1 MiB; frontmatter is limited to 16 KiB by default, at most 64 KiB. Limits and rejected entries are represented explicitly. Individual names use a conservative ASCII subset of up to 64 characters; the reserved `synced` folder is skipped. Native command directories, managed/plugin/cloud sources, parent discovery, nested discovery and synchronization are outside this implementation.

The metadata parser handles a deliberately restricted YAML subset: single-line scalars, quoted text, multiline text, simple lists and invocation booleans. It reads name, description, argument hints, tool declarations, context, agent, model and compatibility fields. Unknown fields and complex values remain uninterpreted and mark metadata partial. Hooks are identified by field name without exposing their contents. A plain tool declaration is retained as one display string; the host does not reinterpret native permission syntax. No-frontmatter files are listed without deriving a description from their body. Invalid metadata, invalid UTF-8, oversized files and unsafe display control characters reject the entry.

All selected paths and their existing ancestors must be ordinary directories with matching canonical paths and stable identities. Existing symbolic links, junctions, linked skill files, hardlinked files and path traversal are rejected. Reads use an open file handle, bounded buffers, file identity/size/change checks and repeated ancestor validation; replacing a root invalidates that root's result. This protects against observed path substitutions. It is not a filesystem sandbox against a hostile process with the same OS privileges, and the hash describes the observed file only. Referenced resources, scripts and arbitrary plugin components are neither read nor certified safe. Feature flags are hints; an absent flag is not a safety claim.

## Activation remains a separate admission operation

Every current entry has `activation.status: "disabled"` and reason `native-adapter-required`. The protocol's `NativeSkillSupport` describes future native support evidence independently of catalog discovery. `SkillActivationIntent` binds an intended activation to skill ID/hash, workspace, runtime, target, policy version and invocation actor type. These are contracts only. A frontmatter `allowed-tools` declaration never grants Harness authority, and the catalog cannot change the current Codex adapter's disabled skill configuration.

The future Claude adapter must:

1. Pin and test the unmodified installed Claude Code interface, preserving native subscription authentication and billing checks. Installing the SDK or finding `SKILL.md` does not satisfy this gate.
2. Establish which exact native roots and skill versions are loaded, including managed settings, duplicates, nested roots, plugins and native cache behavior. Fail admission if a selected catalog hash no longer matches, or if unapproved sources can introduce execution. No copying a skill into another runtime's prompt to bypass its native policy.
3. Bind activation to the admitted workspace, lease, target, account/configuration evidence and host policy. Treat resource access, shell expansion, hooks, MCP, subagents and model overrides as capability and billing changes requiring their own validated boundaries. Adding a directory must not silently grant broader filesystem access.
4. Honor both native invocation restrictions and host policy; neither can broaden the other. Verify deny ordering and native skill tool-grant behavior with the pinned release. Keep model-only and user-only semantics visible, and require new admission when policies, roots or file content change.
5. Prove cancel/revoke/restart behavior without replaying a side effect. Native skill execution stays inside Claude's engine; Harness coordinates the session and permissions through its adapter.

Tests cover explicit root scope, duplicate names, metadata extraction without execution, absent/partial frontmatter, hashes after edits, bounded enumeration and reads, invalid UTF-8/YAML, control characters, hardlinks and directory junctions/symlinks. No installed personal skill or provider account was read during these fixture tests.
