# Claude Skills integration

Harness catalogs local Claude skill files from the selected workspace's `.claude/skills` directory and an explicitly selected personal skills directory. The Claude Code **2.1.251** adapter uses official Agent SDK **0.3.251** to activate explicitly selected compatible standalone Skills in the native runtime. Selection is bound to content hash and invocation mode; discovery alone grants no execution. [Claude execution scope](V1_CLAUDE.md).

## Native compatibility evidence

Compatibility evidence was checked through **2026-09-07** against the official [Claude Code skills documentation](https://code.claude.com/docs/en/skills); see the [native integration evidence](docs/validation/m1b-claude-native-evidence.md). Claude Code supports project and personal skill directories plus other sources, including plugins and nested directories. For project/personal skills, the directory determines the command; an optional `name` supplies the display label. Frontmatter is optional and belongs on the first line. Invocation flags, tool declarations, model selection, forked contexts, hooks, supporting files and dynamic shell content can affect native execution. Discovery can follow links and native source precedence can select among duplicate names. V1 limits activation to the tested standalone subset described below; the broader native feature set is not enabled. Claude Code extensions also differ from the fields accepted by the Skills API and claude.ai uploads, so a file catalog does not establish portability between those products.

## Implemented host boundary

The privileged `discoverClaudeSkills` operation receives a host-resolved `WorkspaceDescriptor`. It reads only immediate `<skill>/SKILL.md` files below that workspace's `.claude/skills` directory. A `userSkillsRoot` is included only after the user explicitly authorizes that directory. The function never infers the home directory, imports a plugin, reads native credentials/settings, launches a process, fetches remote content, or executes a skill.

The browser receives `SkillCatalog` from `@harness/protocol`; filesystem code stays in the control plane's privileged host entry point. The native desktop folder picker authorizes roots. Renderer-supplied paths must never flow directly to this operation. Display fields are untrusted text, not HTML, Markdown instructions, shell arguments or an instruction source for an agent. The catalog omits skill bodies, referenced content, absolute skill paths, unknown metadata values and raw filesystem errors. Frontmatter descriptions remain user-provided content; they may contain sensitive text and should not enter ordinary telemetry.

Discovery is a bounded snapshot, not a native active-skill listing. Each scan permits 256 directory entries by default, across both roots, with a configurable hard maximum of 2,048. Files are limited to 64 KiB by default, at most 1 MiB; frontmatter is limited to 16 KiB by default, at most 64 KiB. Limits and rejected entries are represented explicitly. Individual names use a conservative ASCII subset of up to 64 characters; the reserved `synced` folder is skipped. Native command directories, managed/plugin/cloud sources, parent discovery, nested discovery and synchronization are outside this implementation.

The metadata parser handles a deliberately restricted YAML subset: single-line scalars, quoted text, multiline text, simple lists and invocation booleans. It reads name, description, argument hints, tool declarations, context, agent, model and compatibility fields. Unknown fields and complex values remain uninterpreted and mark metadata partial. Hooks are identified by field name without exposing their contents. A plain tool declaration is retained as one display string; the host does not reinterpret native permission syntax. No-frontmatter files are listed without deriving a description from their body. Invalid metadata, invalid UTF-8, oversized files and unsafe display control characters reject the entry.

All selected paths and their existing ancestors must be ordinary directories with matching canonical paths and stable identities. Existing symbolic links, junctions, linked skill files, hardlinked files and path traversal are rejected. Reads use an open file handle, bounded buffers, file identity/size/change checks and repeated ancestor validation; replacing a root invalidates that root's result. This protects against observed path substitutions. It is not a filesystem sandbox against a hostile process with the same OS privileges, and the hash describes the observed file only. Referenced resources, scripts and arbitrary plugin components are neither read nor certified safe. Feature flags are hints; an absent flag is not a safety claim.

## Explicit native activation

The read-only catalog keeps `activation.status: "disabled"` with reason `native-adapter-required`. This describes discovery, not the capability of an admitted session. The desktop separately checks Claude readiness and offers user/model invocation selection for compatible entries. At most 16 selections are admitted. Codex rejects Skill activation.

`SkillActivationIntent` binds the selection to skill ID/hash, workspace, runtime, target, policy version and invocation actor. The host rebuilds these bindings from its own refreshed catalog; renderer paths and policy claims are not trusted. Starting stages the exact unchanged `SKILL.md` bytes in a private, generated native plugin with a namespaced command. The adapter checks that native initialization discovers each selected command and no unexpected namespaced commands. Source and staged hashes/structure are rechecked before use and native permission responses.

Only standalone `SKILL.md` files are supported. A selected directory containing supporting files is rejected. Dynamic shell substitutions, referenced resources, hooks, forked contexts, model overrides, tool declarations and broader plugin components are unsupported. Invocation metadata is enforced: user-only and model-only choices cannot override native restrictions. Cataloged native tool declarations grant no Harness authority and cannot be activated in V1. Skills stay within the session's Read/Edit/Write boundary, with protected approval for writes and shell/network tools disabled.

User invocation is passed through the native command mechanism; model invocation uses the native Skill tool for the admitted command only. Skill bodies are not converted into a Codex prompt. Source changes, ambiguous names, staged plugin additions or policy changes reject the activation rather than silently reload new instructions. Clean resume revalidates the original bound selections; uncertain Claude recovery remains blocked.

## Validation

Discovery tests cover explicit roots, duplicate names, metadata, partial frontmatter, content hashes, bounds, invalid UTF-8/YAML, unsafe control characters and linked paths. Activation tests cover unchanged native staging, invocation restrictions, hash/policy binding, modified sources/plugins and rejection of unsupported native features. Permission tests cover interruption and late revocation while a Skill or file check is in progress.

The installed unmodified Claude CLI loaded a generated fixture Skill through the official SDK during a no-prompt initialization check. That proves native discovery for the staged subset, not successful provider invocation. No personal installed Skill or provider prompt was used by those fixtures. The subsequent real acceptance run acknowledged one coding prompt, then hit Claude's weekly rate limit before reaching the prepared Skill. The Skill was not invoked and its exact bytes were preserved. Live Skill execution remains pending.
